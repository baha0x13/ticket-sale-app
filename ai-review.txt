CI PIPELINE REVIEW — ticket-sale
=================================

Overall: Solid foundation. Staged security gates (secret-scan/SAST/trivy all
gating push-images), matrix strategy per-service, and artifact-based image
handoff between jobs are good instincts. But there are real gaps and a
couple of actual bugs.


REAL BUGS
---------

1. `lint-and-audit` doesn't lint anything
   Current steps:
       - run: npm ci
       - run: npm audit --audit-level=high
   This is a dependency audit job, not a lint job. There's no `npm run lint`
   / eslint call anywhere. Fix:
       - run: npm run lint
       - run: npm audit --audit-level=high

2. No unit test step exists anywhere
   `compose-integration-test` runs a smoke test against the whole stack,
   but nowhere do you run actual unit tests (`npm test`). Integration/smoke
   tests catch wiring issues, not logic bugs in individual functions. This
   is the biggest gap — add per service (e.g. in lint-and-audit or a
   separate job):
       - run: npm test -- --ci

3. `frontend` is excluded from lint/test matrix but included in build matrix
   `lint-and-audit` and `compose-integration-test` only cover
   [api-service, auth-service, movie-service, notifications-service].
   `frontend` skips straight to `build-images` and `trivy-scan` with zero
   code-quality or test coverage. Even if frontend testing looks different
   (e.g. Vitest/Playwright), it should have something in the pipeline.


ARCHITECTURAL ISSUE: NOT TESTING WHAT YOU SHIP
-----------------------------------------------

`compose-integration-test` does `docker compose up -d --build`, which
builds images from docker-compose.yml. Then `build-images` does a
completely separate `docker build ./${{ matrix.service }}` for the actual
artifact that gets scanned and pushed. These are two independent builds —
if the compose file uses a different Dockerfile, build args, or target
stage than the standalone build, you could pass integration tests against
one image and ship a subtly different one. Tighten this: build once, reuse
that exact image for both the compose test and the pushed artifact.


ORDERING / EFFICIENCY ISSUE
----------------------------

`build-images` (5-service matrix, real compute cost) runs right after
`compose-integration-test`, with no dependency on `secret-scan` or `sast`.
Those two run fully in parallel and only gate `push-images`. Net effect:
if Semgrep finds a critical SAST issue or Gitleaks finds a leaked secret,
you've still spent the compute building and Trivy-scanning all 5 images
before anything fails. Fail-fast principle says cheap/fast checks should
gate expensive ones:

    build-images:
      needs: [lint-and-audit, compose-integration-test, secret-scan, sast]

(Small cost: build-images waits slightly longer to start; usually worth it
since secret-scan and sast are fast.)


MISSING OPERATIONAL HYGIENE
-----------------------------

- No concurrency control — rapid pushes to the same branch/PR queue up
  redundant full runs. Add:
      concurrency:
        group: ${{ github.workflow }}-${{ github.ref }}
        cancel-in-progress: true

- No timeout-minutes on any job — a hung `docker compose up --wait` or a
  stuck smoke test script can eat Actions minutes silently. Set a sane
  timeout per job (e.g. timeout-minutes: 15).

- No least-privilege `permissions:` block except on push-images. By
  default, GITHUB_TOKEN gets broad permissions unless restricted
  workflow-wide. Add at the top:
      permissions:
        contents: read
  and only elevate (packages: write) on the specific job that needs it —
  which is already done correctly for push-images.

- No path filtering — every push/PR to master runs the full 5-service
  build + integration stack + all scans, even for a README change. Add:
      on:
        push:
          branches: [ master ]
          paths-ignore: [ '**.md', 'docs/**' ]
        pull_request:
          branches: [ master ]
          paths-ignore: [ '**.md', 'docs/**' ]


WORTH CONSIDERING (STRONGER SUPPLY-CHAIN GUARANTEES)
-------------------------------------------------------

- Image signing: cosign sign after push-images, so a cluster admission
  controller can verify provenance before deploying.
- Dockerfile linting (hadolint) — catches insecure base images, missing
  USER directives, etc., before Trivy even runs.
- SBOM generation (syft) alongside the image push, useful for future vuln
  triage without rebuilding.


WHAT'S ALREADY GOOD — DON'T CHANGE
-------------------------------------

- Matrix strategy per-service is clean and scales well.
- Passing images between jobs via docker save / artifact / docker load
  instead of rebuilding in every job — avoids drift from rebuilding twice
  for build vs scan.
- push-images correctly gated on github.ref == 'refs/heads/master' + push
  event — PRs build and scan but never push, exactly right.
- fetch-depth: 0 on the gitleaks job — correct, a shallow clone would miss
  history.
